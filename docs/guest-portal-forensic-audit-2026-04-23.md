Blunt truth: current `apps/guest-portal` is a mixed Next UI and SEO shell backed by Fastify, not a pure thin UI and not a self-contained BFF. The current source tree has no `app/api` route handlers and no `lib/server` runtime directory, but the browser still owns substantial orchestration for checkout, tickets, auth UI, profile editing, discovery filtering, and venue interactions.

Counts: the raw tree contains 7321 files and 2824 directories including generated/vendor output. Excluding `node_modules`, `.next`, and `.turbo`, there are 364 source/config/test/asset files and 43 App Router entry files. Source `app/api` is absent; current generated output and git history still mention old local route handlers.

Runtime truth: browser calls go through `lib/api/client.js` and `lib/client/gateway.js`, then hit `/api/v1/*` in the Next app, which `next.config.mjs` rewrites to `http://localhost:4000/api/v1/*`. Server-rendered public/SEO routes use `lib/api/server.js` and call the Fastify base URL directly. Fastify registers guest-facing route groups in `apps/api-gateway/src/app.ts`, and many domain decisions delegate into `packages/core`.

The biggest architectural lie is in stale docs and old tracked files: several docs still describe Firebase/Firestore direct client ownership, Next.js 14-era behavior, and old `/api/webhooks/payment`/Firestore-transaction flows. The current code uses Next 16, cookie-backed Fastify auth, CSRF headers, generated guest API metadata, and no source `app/api` BFF.

## 9. Hidden Complexity and Ambiguity

- Route translation layer: `resolveGatewayCompatibilityPath` silently remaps friendly/legacy paths such as `/events`, `/hosts`, `/venues`, `/notifications`, `/reservations`, and `/profile/:id` before the actual request. Evidence: `lib/client/gateway.js:5-83`.

- Dual transport model: browser calls `/api/v1/*` through Next rewrites, while server components call the gateway base URL directly. Evidence: `next.config.mjs:57-64`, `lib/api/client.js:69-114`, `lib/api/server.js:1-63`.

- Multiple API clients: `guestApi`, `guestApiFetch`, `guestApiJson`, `gatewayFetch`, `gatewayJson`, `publicDiscovery`, `guestServerJson`, and raw external `fetch` all coexist. This makes final ownership hard to read from callers alone.

- Source vs git/generated drift: source `app/api` and `lib/server` are gone, tests require them gone, but git still tracks deleted files and `.next` may still contain generated artifacts from the old tree.

- Frontend-owned domain shaping: homepage buckets, explore filters, host/venue filters, ticket grouping, pending reservation recovery, queue polling, and profile crop state are client-side.

- Passive RSC wrappers: many route files are tiny wrappers around client `PageClient` files, so route existence does not imply server ownership. Evidence examples: `app/checkout/[eventId]/page.jsx:1-5`, `app/tickets/page.jsx:1-?`, `app/profile/page.jsx:1-5`.

- Boundary tests can create false confidence: tests mostly assert file contents and absence/presence, while active user branches like ticket share modals can still be broken.

## 13. Repo Truth Conclusions

Guest Portal today is a gateway-backed Next app with public SEO server wrappers and a large browser runtime. It is not the old local BFF, because the source `app/api` and `lib/server` trees are gone. It is also not a pure execution-less UI proxy, because browser components still own major workflow orchestration, response shaping, local caches, localStorage recovery, polling, and UI-domain state.

Clean parts: source backend boundary removal is real; generated guest API/OpenAPI alignment is guarded; auth moved to cookie/CSRF gateway calls; public SEO pages fetch through the server gateway seam; tickets and notifications have React Query feature seams.

Half-migrated/misleading parts: checkout remains a large browser orchestrator; vanity links have server and client resolution; venue menu exists but ignores backend menu payload; docs describe old Firebase/direct-API architecture; scripts still call deleted modules/old routes; git HEAD still tracks many now-deleted route/server files.

Highest-confidence truths: current source has no `app/api`; current source has no `lib/server`; Fastify is registered as the canonical `/api/v1` owner; tests pass 66/66 but mostly protect boundaries; active share/transfer ticket modals are buggy; docs are stale enough to be unsafe as architectural truth.

Unknown/not verified: live deployed routing/environment variables, whether production has a clean build artifact without stale `.next`, actual Firebase data shape in production, real browser execution of every modal branch, scanner/mobile flows outside this app, and whether the deleted files are intentionally staged for commit or only local WIP.
